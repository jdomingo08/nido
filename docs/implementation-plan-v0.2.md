# Needle — Implementation Plan v0.2

Status: **For final review before Phase 0 begins.**
Date: 2026-04-24
Previous: v0.1 (inline in brainstorming thread)

---

## 1. Product summary

Needle is a multi-agent weekly activity planner for families with young kids. Every morning a parent or caregiver sees 4–6 age-appropriate, well-balanced activities per kid per day, proposed the night before by six cooperating LLM agents (weather, ages, methodology, balance, history, materials) reasoning over the family's context: ages, allergies, nap schedule, preferred methodology, values, dislikes, local forecast, and a 7-day rolling history. The parent approves or dismisses each proposal swipe-style on mobile web, or via a modal on desktop. A balance dashboard tracks each kid across eight categories and nudges the agents toward rebalancing. Activities are generated by an LLM (no human-curated library) with enough depth that a parent can execute cold: materials, setup, step-by-step instructions, parent scripts, variations, troubleshooting.

## 4. Security & compliance

- **Row-Level Security** on every user-facing table. Policies keyed on `family_id = current_family_id(auth.uid())` via a helper SQL function. `admin_*` tables restricted to service role only.
- **CORS**: Next.js middleware allowlist — production domain(s) + Vercel preview domains + `localhost:3000`. Everything else rejected.
- **Security headers** via middleware:
  - `Content-Security-Policy` with per-request nonces (script-src 'self' 'nonce-…')
  - `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
  - `X-Frame-Options: DENY`
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=(self)`
- **Secrets**: OpenAI key server-only (never in client bundle). Stored in Vercel env vars for prod + preview + dev.
- **Rate limits**: per-IP and per-user on `POST /api/week/generate` and `POST /api/activities/:id/regenerate`.
- **Sessions**: Supabase Auth cookies `httpOnly + secure + sameSite=lax`.
- **PII scope**: kid names, ages, allergies. No SSNs, addresses beyond city, no financial data. US-only hosting.

## 6. Activity library — the core IP

### 6.1 Template schema (lean)

```ts
ActivityTemplate {
  id, locale, title, summary
  bucket, methodology
  age_min, age_max
  duration_min, prep_time_min
  skills_developed[]
  materials[] { item, quantity, note, substitutions[] }
  setup
  execution_steps[] { order, instruction, parent_script, duration_est_min }
  variations { easier, harder }
  troubleshooting
  cleanup
  safety_notes
  signs_it_worked
}
```

### 6.2 Two-pass generation

**Pass 1 — Skeleton (cheap, fast, `gpt-4o-mini`)**

Runs at family onboarding. Produces ~500 activity templates covering the bucket × methodology × age-range space. Each row has only: `title, summary, bucket, methodology, age_min, age_max, duration_min, materials[], weather_suitable[], embedding`. Marked `hydrated = false`.

**Pass 2 — Hydrate (rich, `gpt-4o`)**

Triggered the first time any family member opens or approves an activity. The LLM expands the skeleton into the full template above. Result is written back to the **global** `activity_templates` table (not scoped to one family). Marked `hydrated = true`. Future families who get the same template retrieve the hydrated version for free.

Net effect: the onboarding cost is small; hydration cost is paid once globally per activity; popular activities amortize their hydration cost across the whole user base.

### 6.3 Validator

After every skeleton or hydrate call, a `gpt-4o-mini` validator enforces:

1. **Age appropriateness** — materials and steps match the declared `age_min..age_max`.
2. **Safety** — no choking hazards for under-3s, no unsupervised water/sharp/hot for relevant ages, no listed allergens conflicting with family constraints.
3. **Practicality** — materials realistic for a household, quantities non-zero, steps non-empty.
4. **Voice** — lowercase, warm, not preachy. Few-shot examples in the prompt enforce tone.
5. **Duplicate check** — cosine distance against existing `activity_templates.embedding`; if too close to an existing template, reject.

Anything the validator is unsure about gets `review_status = 'flagged'` and lands in `activity_flags` for admin review. Flagged templates are never proposed to users until an admin clears them.

### 6.4 Manual review queue

Admin dashboard surface:

- **Open flags** — template preview + validator reason + approve / edit / reject buttons.
- **User reports** — any user-flagged activity (future "report this" UI) lands here too.
- **Health score** — per-template metric (approvals − dismissals − flags) to surface underperformers for retirement.

### 6.5 Global templates, render-time personalization

Templates are **global and shared across families**. At render time the client swaps in:

- Kid names (`"Luna"` replaces `{{kid_name}}`)
- Locale (template already locale-bound, but dynamic copy like "the whole day" stays per-UI-locale)
- Known kid tags (e.g., a dinosaur-loving kid sees `{{theme}}` rendered as "dinosaur" where the template supports it)

This keeps the library lean and shared; personalization is cosmetic.

### 6.6 Library growth

- Weekly **library extension job** per family: if the retrieval pool shrinks below a threshold (e.g., < 200 candidate templates matching the family's age/methodology profile), generate 20–50 new skeletons.
- Weekly **health pass**: templates with dismissal rate > 60% and no completions are auto-retired from active retrieval but stay in the DB for analysis.

## 7. Weekly orchestrator

### 7.1 Trigger

Vercel Cron, nightly at 3am local time (per family, dispatched based on `families.timezone`). One run produces next-day's proposals; Sunday's run produces the whole upcoming week.

### 7.2 Inputs

- Family: methodology, values, constraints, dislikes, locale
- Kids: ages, tags
- Last 7 days of `history_entries` per kid
- 7-day weather forecast for `families.city`
- Current `activity_templates` pool (filtered by locale, age, weather, constraints)
- Admin status (is the family disabled? is the global kill switch on?)

### 7.3 Algorithm

```
1. Retrieve: pgvector semantic search over activity_templates, filtered by:
   - locale match
   - age overlap with any kid in family
   - weather compatibility
   - materials ∩ family.dislikes = ∅ (via constraint tags)
   - not proposed to this family in last 14 days
   - review_status = 'approved'
   Top-K = 150 candidates.

2. Balance analysis (deterministic, no LLM):
   - compute per-kid 7-day minutes per bucket
   - flag light buckets (< 70% of ideal × 7)
   - tag candidates that would fill light buckets

3. Rerank (gpt-4o, structured output):
   - input: candidates, family context, balance flags, kid tags, density setting
   - output: JSON — for each day, N primary proposals + 2N alternates, each with:
     { template_id, start_hour, duration, kid_ids, badges[], reasoning }

4. Validator pass: re-check every proposal for constraint compliance.

5. Hydrate: any proposal whose template is still skeleton-only gets hydrated
   before write (so cards are readable the moment the family opens them).

6. Write: week_plans + activities + activity_alternates rows.

7. Append llm_calls ledger rows for all OpenAI calls.

8. If retrieval pool was thin, queue library extension job.
```

### 7.4 Cost projection (ballpark)

Per family per week, first run:

| Step | Model | Tokens in | Tokens out | Cost |
|---|---|---|---|---|
| Retrieval context | — | — | — | $0 (pgvector only) |
| Rerank | gpt-4o | ~40k | ~15k | ~$0.25 |
| Validator | gpt-4o-mini | ~10k | ~2k | ~$0.003 |
| Hydrate (5 new templates avg) | gpt-4o | ~15k | ~20k | ~$0.25 |
| **Total** | | | | **~$0.50** |

After the library saturates, hydrate cost trends to near-zero and weekly cost drops to ~$0.25/family. Well under any reasonable cap.

## 8. Regenerate flow

User swipes-left on a proposed activity:

1. Client `PATCH /api/activities/:id` → status `'dismissed'`.
2. Server reads `activity_alternates` rows for that activity, ordered by `rank`.
3. First unused alternate is promoted: new `activities` row is written for that slot with status `'proposed'`.
4. Dismissed template's `times_dismissed` counter increments.
5. **No LLM call** unless the alternates pool is empty — then trigger a per-slot fresh generation (still gpt-4o-mini for speed).

Client sees the next alternate instantly. True cost: ~$0 for the first 2 swipes per slot.

## 9. History & completion tracking

- **Default: passive auto-complete.** Approved activities flip to `status='completed'` at `start_hour + duration_min` of their day. This writes `history_entries` with `source='auto'`.
- **Evening nudge (8pm local, per family):** push notification asking the parent to confirm. Response updates the day's `history_entries` rows:
  - `yes` → keep auto row, change `source` to `'confirmed'`
  - `no` → delete the auto row
  - `skipped` → leave auto row, flag `source='auto'` so balance weighting can discount
- **Opt-out:** evening nudge toggleable in Settings (on by default).

This gives us usable data on day 1 without per-activity friction, and lets motivated parents correct it.

## 10. Notifications

- Web Push via VAPID keys.
- Subscription UI appears once the user enables `per_activity_reminders` in Settings (explicit opt-in, not prompted on first visit).
- **Per-activity reminders**: scheduled at `start_hour - reminder_minutes_before` (default 15). Server-side cron sweeps `activities` with `scheduled_reminder_at` in the next 5 minutes and pushes.
- **Evening nudge**: always sent if `notification_preferences.evening_nudge = true`.
- **Quiet hours**: hard-coded 9pm–7am local, no pushes sent.

---

## 11. Localization

- `next-intl` with `messages/en.json` and `messages/es.json` for all UI chrome.
- `families.locale` stored per-family; user-selectable in Settings.
- **Activity content**: orchestrator passes `locale` into every LLM call. Templates are locale-bound (`activity_templates.locale`), so retrieval filters by it. An EN family only sees EN templates; ES family only ES.
- **No mixed strings anywhere.** The prototype's "cocinando · cortar plátano maduro" aesthetic is dropped. If a family wants Spanish, everything is Spanish.
- Adding a third locale later is a schema-safe op (add rows, generate in new locale, filter on `locale`).

## 12. Admin surface

Separate `/admin` route, gated by a `is_admin` claim on the auth user. Tables and views:

- **Families** — list, search, per-family cost (rolling 7d), status, override cap.
- **Cost ledger** — filterable `llm_calls` view, aggregations by model + purpose.
- **Library** — template count by locale/bucket/methodology, health scores, hydrate rate.
- **Review queue** — open `activity_flags`, approve/edit/reject.
- **Kill switch** — flip `admin_config.global_orchestrator_enabled = false` to pause all nightly runs.
- **Per-family override** — set/unset `family_admin_overrides.weekly_cost_cap_usd` or disable a family entirely.

V1 ships with no cap enforced by default (null = no cap). The infrastructure is live so caps can be turned on without a deploy.

## 13. Agent transparency UI

Three levels, default `transparent`:

| Level | Card shows | Modal shows |
|---|---|---|
| `hidden` | Title, time, kid pills. No badges. | Materials + steps + scripts only. No agent reasoning. |
| `subtle` | 2–3 badges (e.g., ☀ sunny, montessori, post-nap). | Badges + materials + steps. No full reasoning chain. |
| `transparent` (default) | Same badges. | Full reasoning chain: *"method_agent picked montessori. weather_agent cleared (sunny, 84°). balance_agent flagged Luna's quiet bucket was 40% light. history_agent: not proposed in 14d. materials_agent: you have everything."* |

Toggle lives in Settings. Setting applies globally for the family (not per-user inside the family).
